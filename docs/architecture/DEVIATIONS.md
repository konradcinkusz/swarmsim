# Open deviations

Per [`00-REFERENCE-ARCHITECTURE.md` §3a](https://github.com/konradcinkusz/architecture-standards/blob/main/docs/architecture/00-REFERENCE-ARCHITECTURE.md#3a-known-open-deviations):
an unacknowledged gap from the constitution is drift; an acknowledged one is a decision.
This table is that acknowledgment. When a row is fixed, it is deleted, not marked done.
A row whose trigger has fired says so — a fired trigger nobody acted on is the same
drift this register exists to prevent, just with better paperwork.

| Principle | Deviation | Since | Reasoning / trigger to close |
|---|---|---|---|
| P1 (AppHost is the composition root) | No .NET Aspire AppHost. `SwarmApi.Api` is a single ASP.NET Core project; the development composition root is `docker/docker-compose.yml`, which now orders startup with a healthcheck (`api` waits for rosbridge). | M3 | See [ADR-0002](../adr/0002-composition-root-split.md). Trigger: a second .NET service of this repo's own (the M5 mission layer was the planned one). The compose file already carries four services, so revisit if startup ordering needs more than one healthcheck edge. |
| P2 (shared kernel) — partly | `SwarmApi.ServiceDefaults` is guarded by an architecture test and a CI size ceiling (2026-09-22), but JWT wiring lives in `SwarmApi.Infrastructure` rather than the kernel, and there is no OpenAPI document. | M3 | One service validates tokens, so the kernel has nobody to share them with yet; an OpenAPI generator would be a second third-party runtime package (see the README's dependency budget). Trigger: a second service validating the same tokens, or the first consumer outside this repository needing a machine-readable contract. |
| P5 (JWT / asymmetric signing), narrowed | `SwarmApi.Api` validates JWT bearer tokens (RS256, JWKS) from an external `authservice` instance and, when Enforced, denies by default: every endpoint needs a token unless [API-SURFACE.md](API-SURFACE.md) lists it as open — the dashboard's static files, `/health`, `/alive` and the `GET` reads — so every write is attributable, and the identity that proposed a mission plan cannot approve it ([ADR-0009](../adr/0009-agent-write-gate.md)). The dashboard has no login UI, so in Enforced mode every one of its buttons gets a 401: start, approve, reject, dispatch — and **abort and land-all**, so an operator with only the dashboard cannot stop the swarm; approval and stopping then go through the API with a token. In Open mode nobody is identified, so separation of duties does not apply. Tokens carry no tenant claim yet. | M3; narrowed 2026-09-21; deny-by-default 2026-09-22; approval gate 2026-09-22 | See [ADR-0005](../adr/0005-mcp-server-and-bearer-auth.md) and ADR-0009. Trigger: a login flow for the dashboard (it closes the stop-button gap too), a requirement to distinguish *readers*, or per-tenant token claims (needed by [ADR-0006](../adr/0006-multi-tenant-isolation-model.md)'s orchestrator). |
| P7 (Fly.io) — `swarmsim-api` | No `fly.toml` for the API and scenario path. | M3 | Target decided in [ADR-0007](../adr/0007-deployment-target.md): a cheap, scale-to-zero Fly app. **Trigger fired 2026-09-21** — ADR-0007 made this unit's trigger "issue #12's scenario library lands", and it has. Still not actioned, but the reason changed on 2026-09-22: the scenario instrument now runs as a CLI and as a GitHub Action inside the caller's own CI ([ADR-0008](../adr/0008-scenario-instrument.md)), so the hosted path is for storing and comparing runs, not for running them. Close by deploying, or re-date the trigger with a reason. |
| P7 (Fly.io) — `swarmsim-sim` | No deployment path for the Gazebo/PX4/ROS 2 stack. | M3 | Per ADR-0007 and ADR-0006: per-tenant, per-run instances, never a standing deployment. Trigger: first pilot with a real operator, and the ADR-0006 orchestrator existing. |
| P12 (tag-driven CI/CD, change detection, ordered deploy) | CI builds and tests on every push/PR; `release.yml` creates a GitHub Release from a `v*` tag; there is no deploy job and no tag has been cut. | M3 | Follows from the P7 rows — nothing to deploy to yet. Trigger: same as P7 `swarmsim-api`. |
| P15 (OTLP observability) | No OpenTelemetry exporter wired. `SwarmApi.ServiceDefaults` exposes `/health` and `/alive` only. | M3 | No collector endpoint exists to export to yet, and P8's "visible degradation" is met without it: `/health` reports the bridge's live mode (Degraded while rosbridge is disconnected), the age of the last swarm state, and the auth mode. Trigger: first deployed environment with an OTLP collector. |
| P3 / P4 (service owns its database, `MigrateAsync`) | `SwarmApi.Api` is stateless: swarm state lives in memory (real: rosbridge-fed; fallback: simulated engine), and missions, mission plans and idempotency keys are not persisted across restarts — a restart forgets a pending approval and its code, and a replayed key after one runs its write again. | M3; plans and keys 2026-09-22 | Outside the rule, not an exception to it (constitution P4 note): there is no entity model and no schema to migrate. Trigger: a requirement to recall a mission, a plan or a scenario run after a restart, or more than one API instance (keys and plans would then need a shared store). |

Everything not listed here is met as stated in `docs/architecture/README.md`'s
compliance checklist.
